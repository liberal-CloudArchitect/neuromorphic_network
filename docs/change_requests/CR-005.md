# CR-005：按实测吞吐修订 P4 mechanism 资源预算

## 触发证据

`p4-protocol-v1` 的两次正式 mechanism 均在冻结的 24 小时上限安全停止，且都没有程序异常或 checksum 损坏：

- `p4-mechanism-fb53443a-20260722T160041Z` 完成 15/24；旧标量 SmallGraph rollout 是主要可消除瓶颈。
- `p4-mechanism-bcbbe9e2-20260727T044447Z` 在批量 rollout 修复后完成 8/24；seed 17 的完整八 cell 已实际耗时 `44,080.27 s`（12.24 小时），其中四个重训练 cell 的 12,600 updates 耗时 `34,950.28 s`（9.71 小时）。即使不计第二天约十小时的疑似系统挂起，按三个 seed 线性外推也约需 36.7 小时。

新进程在同一 seed 29 checkpoint、MPS、256 个冻结 test 图上的定向复现耗时 `8.68 s`，成功率 `0.88671875`。因此第二次 run 最后的长空窗不是损坏 checkpoint 的正常推理成本，但 24 小时预算即使没有该空窗也无法容纳完整矩阵。

这些事实只涉及完成数、时间、步骤和产物完整性；未查看缺失 seed 的科学效应，也未据已有指标改变假说、阈值或模型。

## 批准变更

- 建立 `p4-protocol-v2`，将 24-cell mechanism 的累计墙钟上限从 24 小时调整为 48 小时。
- 架构、任务版本、split seed、正式 seed、样本量、训练 step 上限、early stop、optimizer/preset、矩阵、干预、bootstrap、Holm family 和所有科学阈值保持不变。
- runner 在 evaluation 与 live rollout 内持续更新阶段 heartbeat，明确记录 task、split、distribution、完成量和 rollout turn。
- 每个 cell 结束后释放 Python 对象和 MPS allocator cache，降低长进程缓存滞留风险；不改变模型状态或数值路径。
- full 的冻结上限仍为 72 小时；只有新协议 mechanism Gate 通过后才能启动，届时再以完整机制实测决定 72 小时是否可行，不预先扩张 full 预算。

## 证据链与禁止事项

- 两个 v1 run 都保持 `RESOURCE_LIMIT / INCONCLUSIVE`，不得恢复、拼接或并入 v2 统计。
- 源码和 protocol hash 改变后，必须在同一 clean SHA 重新通过 CI、qualification 和 pilot，再从新 run ID 启动全部 24 个 mechanism cells。
- qualification/pilot 只证明路径与选择，不能替代正式 Gate。
- 若 v2 在 48 小时内仍不完整，继续保留失败证据并停止；不得临时删 cell、删 seed、缩样本或放宽科学阈值。
