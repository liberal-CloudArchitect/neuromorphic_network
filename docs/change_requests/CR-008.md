# CR-008：冻结 Windows CUDA mechanism 通道

## 决策

在 `CR-007` 的设备隔离 pilot 基础上增加 `cuda-mechanism`。该通道固定使用 Windows 11、RTX 4060 Laptop GPU、Python `3.12.13`、PyTorch `2.12.1+cu126`、CUDA runtime `12.6` 与驱动 `572.16`，消费 `artifacts/p4-cuda/` 下同 SHA 的 qualification 与 pilot 锁。

机制矩阵保持 24 cells、seeds `[17,29,43]`、正式数据规模、每任务最多 5,000 updates、10,000 次配对分层 bootstrap 和 48 小时累计墙钟。optimizer 必须由 CUDA pilot 锁注入；配置中的默认 `preset-3` 只用于静态解析，不得覆盖锁内选择。

## 科学与设备口径

- 所有 full/干预/control 配对在同一 CUDA 设备、wheel、driver 与 seed 上执行；不得把 MPS cell 拼入 CUDA mechanism。
- 预测因果、预测质量、稀疏非劣性、Holm family 与否证阈值保持 `p4-protocol-v2` 不变。
- 数值健康要求所有 loss、梯度、state 与逐样本指标有限；checkpoint 恢复采用现有 CUDA RNG/state 契约。
- 参数与 MAC 是设备无关的结构计数；wall-clock、峰值内存和延迟仅在 RTX 4060 内比较，不能与 MPS 直接合并。
- CUDA mechanism 通过只生成设备专属 mechanism lock。CUDA full 仍需另行冻结，不由本 CR 授权。

## 前置与验收

- clean `HEAD == origin/main`，同 SHA GitHub Actions 绿色。
- 同 SHA CUDA qualification 8/8 且 checksum 有效。
- 同 SHA CUDA pilot 4/4，通过冻结规则选择 preset 并生成有效锁。
- controller 的 start/status/logs/resume/stop/verify 使用 CUDA 锁命名空间，拒绝 MPS 锁替代。
- 24 cells 必须全部完成才能裁决；失败、缺 seed 或资源上限均保持 `INCONCLUSIVE/FAILED`，不得生成通过锁。
