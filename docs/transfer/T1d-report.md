# T1d 结果：按读出注意力寻址的门控没有可靠地修复多情境缺陷；对单情境无害

本报告属于 T track 的探索层，不构成任何 Gate 证据。协议在运行之前已冻结并提交（`440a0c8`）；冻结前只在非正式 seed 996 上用 train/validation 做过一次设计检查，设计未改动（已在协议第 7 节披露）。正式运行耗时 9,777 s（9 个 CPU 进程）。

## 2. 裁决（协议 5.1）

- **H1 不支持：就这种寻址而言无效。** 把 surprise 偏置按读出注意力分配到槽上，恢复准确率只比全局门控高 1.2pp，CI 包含 0；逐 seed 差值在 −3.7pp 与 +4.6pp 之间。T1c 第 4 节的事后推测（“门控不按情境寻址是更新缺陷的原因”）没有得到支持。
- 多情境下 GRU 仍更好（恢复 −2.5pp、OOD −1.8pp，非劣都不成立），与 T1c 一致（T1c：−3.6pp、−2.2pp）。
- **单情境安全（H5、H6）**：寻址门控与全局门控在单情境上完全相同（+0.0pp），与 GRU 的 OOD 差 −0.5pp，在 2pp 界内。
- **对 CR-015 的建议**（按协议 5.1 的预设规则）：`working_memory.v2` 保留 T1b 的全局门控；在 CR-015 中把“多个独立变量时不如 GRU”列为已知缺陷。

## 4. 事后分析（未预注册）：寻址在 7/10 个 seed 上追平 GRU，但不可靠

（test 恢复准确率）

- 在 7 个 seed 上（901、902、904、905、908、909、910），`enr_addr` 的恢复为 0.735–0.766，平均 0.755，与同 seed 的 GRU（0.759）几乎相同；另外 3 个 seed（903、906、907）落后 5.8–8.8pp。
- 落后的 seed 并不是寻址失败：它们的读出注意力同样集中且一致（0.96–1.00）。它们的恢复曲线在 10,000 次更新时仍在上升（例如 seed 903 在 lr = 1e-3 下从 0.711 升到 0.733），而且 seed 903 按 validation 总体准确率选中了恢复较差的 lr = 3e-4。差距更像是**学得慢**，而不是结构上限。
- 因此一个可能的解释是：按内容寻址消除了全局门控的结构限制，但让学习变得不稳定。这是基于 seed 分组的事后描述，没有被检验；要确认需要更长的预算或新的协议。

## 5. 结论

1. **按预注册裁决，按读出注意力寻址的门控没有可靠地改善多情境下的更新**（H1 +1.2pp，不显著）。多情境下 GRU 仍更好（−2.5pp）。
2. **寻址对单情境无害**（H5、H6 非劣），槽结构对未切换情境的保护也保留。
3. 事后看，寻址在多数 seed 上能追平 GRU，但 3/10 个 seed 学得明显慢；目前不足以把它推荐为 `working_memory.v2` 的门控。
4. 对 CR-015：按协议的预设规则保留全局门控，把多情境列为已知缺陷。若想继续，可以另立协议检验“寻址门控 + 更长预算”是否稳定地追平 GRU。

## 6. 解释边界

- 只检验一种寻址方式与一种任务配置（3 个情境、4 个槽）。
- 第 4 节是事后分析；“学得慢”的解释没有被检验。
- GRU 比工作记忆多 5.5%（部分 A）/ 5.6%（部分 B）的参数。
